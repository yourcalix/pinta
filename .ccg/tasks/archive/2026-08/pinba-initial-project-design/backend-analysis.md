# GPT 5.3 Codex Spark 后端/业务分析摘要

## 结论摘要

- 将“拼吧”定义为社交化活动撮合与协作平台。MVP 聚焦“发布—发现—申请—确认—成团—完成—评价/举报”，不默认自营运输、销售商品、托管资金或赔付。
- 使用“通用拼局核心模型 + 场景扩展字段 + 场景规则”覆盖拼车、拼商品和兴趣搭子；成团条件、隐私披露和风险规则必须差异化。
- 首版必须同步建设基本信任安全闭环：联系信息延迟解锁、新号限权、频控、敏感内容初筛、举报工单、人工下架/封禁和不可变审计记录。
- 长期更适合独立后端；MVP 可比较微信云开发与模块化单体后端，但小程序端应经过统一 BFF，避免绑定存储实现。

## 场景差异

| 维度 | 拼车 | 拼商品 | 兴趣搭子/拼好友 |
| --- | --- | --- | --- |
| 关键字段 | 起终点、时间、席位、出行角色 | 商品、规格、数量、预算、交付方式 | 兴趣、活动、社交边界、年龄段 |
| 主要风险 | 精确位置、人身安全、非法营运边界 | 诈骗、质量、付款与交付纠纷 | 骚扰、未成年人、线下见面安全 |
| 首版边界 | 信息撮合，不提供运输服务 | 协同凑单，不做商城和担保 | 活动搭子，不做婚恋或无限制陌生人社交 |

## MVP 与后续阶段

### MVP

- 微信登录与最小用户画像。
- 发布、筛选/搜索、活动详情。
- 申请、发起者审核、参与者确认、人数成团、过期关闭。
- 成团后按规则解锁联系或会合信息。
- 完成确认、结构化评价、举报。
- 基础内容检测、频控、黑名单、运营后台、审计与监控。

### Phase 2

- 路线/预算/兴趣匹配等场景增强。
- 站内沟通、申诉复核、可配置风控、更完整审核能力。
- 个性化推荐、信用能力和运营分析。

### Phase 3

- 在资质、合规和运营能力成熟后评估支付/托管、保险/合作担保、会员和多端扩展。

## 领域模型建议

- `User`、`UserProfile`：账号状态、基础画像、兴趣与安全标记。
- `Activity`：通用拼局，含类型、时间、地域、人数、可见范围、截止时间和状态。
- `ActivityMeta`：按类型和 schema 版本校验的场景扩展字段。
- `Application`：每人每活动唯一，支持提交、批准、拒绝、撤回和过期。
- `Group`、`GroupMember`：成团实例、成员角色、确认状态、加入/退出记录和乐观锁版本。
- `CompletionRecord`、`Review`：完成事实与组内受限评价。
- `Report`、`ModerationCase`、`RiskEvent`、`AuditLog`：举报、审核、风控处置与审计证据。
- 关键写操作需幂等；容量变更必须使用数据库事务与版本控制，保证不超员。

## 状态机重点

- 拼局：`DRAFT → PUBLISHED/RECRUITING → FORMED → IN_PROGRESS → COMPLETED`，并允许从适当节点进入 `CANCELLED`、`EXPIRED` 或 `SUSPENDED`。
- 申请：`PENDING → APPROVED/REJECTED/WITHDRAWN/EXPIRED`；批准后是否还需参与者确认应作为产品决策。
- 成员：`INVITED/APPLIED → CONFIRMED → ACTIVE → COMPLETED`，可进入 `LEFT/REMOVED/NO_SHOW`。
- 举报：`NEW → TRIAGED → INVESTIGATING → RESOLVED → APPEALED → CLOSED`。
- 已发布活动的核心字段需要限制修改；取消、超时、踢出、重复提交、多人争最后名额等异常必须定义可预测结果。

## 技术与非功能建议

- 架构：小程序 + BFF/API + 模块化单体（身份、活动、匹配、信任安全、通知、评价、分析）+ 关系数据库 + 对象存储；缓存、搜索和消息队列按规模渐进引入。
- 列表与地理筛选使用城市/区域和模糊位置；精确会合点只在必要阶段向必要成员开放。
- 关键指标：发布成功率、发布到申请、申请到入团、成团率、完成率、取消/爽约率、举报率、复用率、审核时效、接口错误率。
- 运维能力：操作审计、数据备份、恢复演练、功能开关、城市灰度、按账号/IP/设备的限流和高风险场景关停开关。

## 需尽早决策

1. MVP 首发一个场景还是拼车 + 拼商品两个场景。
2. “拼好友”是否严格限定为兴趣/活动搭子，以及年龄门槛。
3. 是否允许未成年人，若允许需要何种额外保护。
4. 拼车是“乘客找同行”还是允许司机/车主发起。
5. 拼商品是否只做凑单协作，是否展示金额与外部购买链接。
6. 联系方式和精确地点在何时、向谁解锁。
7. 是否需要双确认才能正式占用名额。
8. 已发布活动允许修改哪些字段。
9. 取消和爽约如何记录、何时降权或冻结。
10. 评价公开范围、匿名规则与申诉机制。
11. 举报的处理时效和自动隐藏/冻结阈值。
12. 冷启动是否允许官方或合作方创建认证活动。
13. 首发技术选用云开发还是独立后端。
14. 后续是否可能引入支付/担保，以便现在保留正确边界但不提前实现。

## 主会话综合时需修正的点

- 不直接采用固定的 6—10 周估期，需先明确团队规模和首发场景。
- 不在初稿中承诺未经官方文档/专业审查确认的合规结论。
- 技术设计保持“模块化单体优先、按规模演进”，避免 MVP 一开始堆叠 Redis、搜索集群和消息队列。
