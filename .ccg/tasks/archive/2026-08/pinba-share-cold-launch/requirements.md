# 需求：活动分享卡片与冷启动直达

## 背景

代码级 MVP 已具备公开详情、下架兜底和账号受限反馈，但详情页尚未实现微信原生分享卡片。路线要求分享链接在小程序冷启动、热启动、游客和已有用户状态下均落到正确活动，且不因初始化时序读取错误身份或残留页面数据。

## 目标

- 详情页实现 `onShareAppMessage`，分享路径使用真实分包路径并沿用查询参数 `id`。
- 提供明确、可发现的分享入口；分享卡片标题不得泄露联系方式或内部状态。
- 冷启动和热启动都只加载分享参数指定的活动，不复用上一个页面的活动 ID 或旧内容。
- 分享落地继续允许游客浏览，只有申请等受保护动作才触发登录。
- 缺失、无效、已下架 ID 进入现有安全错误状态，不能停留在永久骨架屏。
- 单页栈下继续使用“返回发现页”稳定兜底。
- 保持 `useMock=true`，不配置真实 CloudBase、订阅模板或官方审核项。
- 本切片完成后先本地提交；待整个 G2 阶段完成并通过复审时，再按项目指南推送 GitHub，不把阶段内半成品标记为 G2 交付。

## 待分析关键点

- 当前 `App.onLaunch` 只有同步配置和 `wx.cloud.init` 调用，公开详情不要求登录；是否确有必要引入全局 readiness Promise，还是应避免制造没有异步初始化来源的等待层。
- 原生右上角菜单和页面内 `open-type="share"` 是否都需要，怎样保持按钮优先级不过度干扰申请/管理主操作。
- `onLoad` 缺少 `id` 时当前页面不会请求也不会退出 loading，需要形成安全 NOT_FOUND 分支。

## 验收

- 分享 payload 的 path 精确为 `/subpackages/activity/detail/index?id=<encoded-id>`。
- 冷启动顺序下先得到并固化 ID，再加载公开详情；不主动登录。
- 无 ID、无效 ID和 `TAKEDOWN` 分别进入受控状态。
- 分享中不包含联系方式、申请备注、内部用户 ID 或处置信息。
- 自动化、项目检查和 CCG 分域复审通过；真机分享卡片保留为真实 AppID 验收项。
