# 分析记录：发现页分页与状态一致性

## 当前源码事实

- `activity.list` 已接受 `cursor/limit` 并返回 `items/nextCursor`，但发现页固定请求 30 条且没有续页状态。
- Memory Store 先过滤再按 offset 分页，并会在 list 中原地把截止活动改成 `EXPIRED`。
- Cloud Store 先 `skip/limit`，再过滤 keyword 和截止时间，可能返回不足一页并错误产生或丢失 `nextCursor`；详情页也不会归一化已截止的招募状态。
- Mock 当前忽略 `cursor/limit` 并一次性返回全部。
- 发布草稿恢复已存在，因此路线图中下一项应直接推进分页和状态一致性。

## GPT 5.5 后端分析

- 保持 API 契约不变，客户端继续把游标当不透明字符串。
- 服务端游标采用基础候选集 raw offset；空值为 0，非十进制整数、负数、小数或非安全整数返回稳定参数错误。
- Memory、CloudBase 和 Mock 都从 raw offset 开始扫描，做 keyword 与截止过滤，收集 `limit + 1` 个可展示项；返回前 `limit` 个，额外匹配项的 raw index 作为下一游标。
- CloudBase 应分批查询直到填满页面、候选耗尽或达到明确扫描上限，不能 `limit` 后简单过滤。
- list/detail 共用读时状态归一化：`RECRUITING && deadline <= now` 对外视为 `EXPIRED`；不在本阶段引入计划任务。
- Memory 不应在公开列表读取时原地修改领域实体，Mock 必须真实执行分页以便测试契约。

## 主会话补充边界

- 公开候选状态仍包含 `RECRUITING` 与 `FORMED`；仅到期的 `RECRUITING` 从列表隐藏，`FORMED` 不因报名截止而消失。
- 客户端不能自行把活动定为最终 `EXPIRED`；本地截止计时只触发一次服务端刷新。
- 筛选/搜索/刷新必须生成新的请求序号；加载更多响应只能追加到同一查询快照，且按活动 ID 去重。
- 首屏失败展示错误空状态；续页失败保留现有卡片并提供非阻断重试。

## 待 Gemini 重点判断

- 首屏 loading、下拉刷新、触底 loading、续页失败和末页提示的最小 UI 层级。
- 320px、小字号/大字号下分页尾部与活动卡片的布局。
- 快速切换 Tab、连续搜索、触底与截止定时刷新同时发生时的交互优先级。
- 页面 `onShow/onHide/onUnload` 的刷新和计时器时序，避免 Tab 首次进入重复请求。

## 网页版 Gemini 3.7 Flash 回传

- 最终结论：【调整后可执行】；Critical 无。
- replace 动作必须抢占 append，续页响应只能在同一查询序号下合并。

- 页尾只保留加载中、加载失败重试和末页三种互斥状态；续页失败不覆盖现有卡片，不使用重复 Toast。
- 通知式页尾重试按钮保持 `88rpx` 热区并提供明确读屏文案。
- 当前页因举报隐藏后完全为空且仍有游标时，可以受控自动补拉。

## 综合校正

- Gemini 示例中的 `++(this._loadSeq || ...)` 不是合法 JavaScript；实现使用显式赋值和查询序号快照。
- 一小时计时护栏到点时若真实截止时间仍未到，只重新排程，不发起无意义的每小时网络刷新。
- 隐藏过滤自动补拉最多一次；若仍为空，保留安全空态或续页入口，禁止无界递归。
- subsequent `onShow` 使用静默 replace 保证新发布、审批和退团后的服务端状态可见；首次挂载仍只请求一次。
