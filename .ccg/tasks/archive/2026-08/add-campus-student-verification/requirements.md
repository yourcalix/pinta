# 需求增强

## 用户目标

在“我的”页面新增“校园学生认证”，视觉与现有“司机任务/司机认证”模块同属一个身份能力层。用户只有完成校园学生认证后，下方个人行程内容才可显示。

## 必须明确的系统边界

1. 学生认证必须有稳定状态，而不是单一前端布尔值：至少覆盖未提交、审核中、已通过、已拒绝/需补资料。
2. 行程隐藏不能只依赖 WXML；服务端“我的行程”接口必须根据可信认证事实 fail-closed，避免绕过。
3. 公开发现页与公开详情仍保持游客可读，不因学生认证破坏零登录浏览规则。
4. “我的”页面的司机认证与学生认证相互独立；司机承接权限继续只信任司机/车辆事实源。
5. 学生认证可能涉及证件或校园身份材料，敏感数据不得进入 Local Storage、公开 DTO、日志或普通用户资料。
6. MVP 开发环境是否自动通过应采用显式环境开关，生产环境不得默认通过。
7. 当前全站用户可见文案不得重新出现已移除的地域字样。

## 待分析决策

- 认证采集字段：学校、学号、校园邮箱、学生证图片中的最小必要集合。
- 是否由用户提交后在开发环境自动通过，生产环境人工审核。
- “下方对应行程”具体范围：我的发布、我的参与、待处理统计、司机任务是否全部受限。
- 已有用户/历史行程迁移与兼容策略。

## 双模型审查后的统一结论

1. 学生认证卡固定放在用户资料卡与 Dashboard 双视图切换之间，作为全局基础门禁。
2. 未通过认证时保留“我的拼车 / 司机任务”切换，但不显示真实统计、通知、行程或司机任务；统一展示“数据仍保留，认证后解锁”的锁定状态。
3. `activity.mine`、通知和 `ride.driver.mine` 等私域请求必须在服务端或统一 Dashboard 契约中先检查可信认证事实，缺失记录视为未认证。
4. 学生认证采用绿色，司机专项认证继续采用低饱和蓝色，二者状态与权限完全独立。
5. 状态枚举优先沿用现有认证命名风格：`NOT_SUBMITTED | SUBMITTED | APPROVED | NEEDS_MORE_INFO | REJECTED`，不采用前端自造的 `PASSED`。
6. 不承诺固定审核时长，不直接展示服务端原始审核备注；前端只映射稳定 reasonCode。
7. 本轮只门禁“我的”私域 Dashboard，不额外扩大到公开浏览或社区发布权限。
