# Web Gemini 3.7 Flash 前端审查提示词

ROLE: frontend reviewer for a native WeChat Mini Program

TASK:
审查一次已经完成的首页重构。目标是严格接近用户给出的 Concept A 暖米白生活方式参考图，同时保留真实业务数据和微信小程序约束。

已实现的产品要求：

1. 页面顺序为：动态用户问候栏 → 空插画 Hero → 三张负边距叠放快捷卡 → 可按需展开的搜索筛选 → “附近拼吧 · 正在发生” → 真实活动流。
2. 文案必须保持：
   - “你好，{{用户昵称}} 👋”
   - “欢迎你回到拼吧”
   - “你的搭子，刚刚好”
   - “发现身边同频的人和活动”
   - “组队拼团 / 看看大家都在聊什么”
   - “琐碎回忆 / 记录第一次成团”
   - “暂定 / 模块占位”
3. Hero 主插画尚未生成，本轮必须保持空槽；不能展示临时图、破图标识或伪造场景。
4. 三张快捷卡的 PNG 图标也尚未交付；当前条件渲染空插槽，后续由用户提供 image2 生成资产。
5. 活动保持原有 46:54 左图右文真实活动卡，不伪造参考图中的邻里动态或图片帖子。首批加载 3 条；“查看更多”按不透明游标每次追加最多 3 条，失败保留已有卡片，不显示虚假总页数。
6. 搜索筛选能力不能删除，但默认折叠，由右上搜索按钮展开，以保持参考图首屏构图。
7. 已删除当前首页“成团记忆”模块；已定稿设计另行归档，未来真实 UGC 分享功能再恢复。

关键视觉参数（750rpx 基准）：

- 页面左右边距 28rpx，底色 #F9F7F2。
- 问候栏最小高 88rpx；头像 64rpx；右侧消息/搜索合并为 176×88rpx 白色胶囊，每个按钮 88×88rpx。
- Hero 高 360rpx，圆角 32rpx，暖白渐变与克制投影；空插画位只使用径向柔光。
- 三快捷卡高 210rpx、间距 16rpx、圆角 24rpx、向上叠压 68rpx；分别为暖黄、柔蓝、浅紫。
- 320px 断点：左右边距 20rpx，Hero 320rpx，快捷卡 190rpx、间距 12rpx、向上叠压 56rpx；所有真实按钮热区仍至少 88rpx。
- 活动骨架与真实卡标准屏最小高 390rpx，320px 为 350rpx。

已完成工程验证：

- `npm run verify`：311 pass、0 fail、1 historical skip；项目静态检查通过（219 JSON、150 JS、21 WXML）。
- 微信开发者工具重新编译成功，首页正常呈现动态问候、空 Hero、三快捷卡和 3 条真实活动，无 WXML 构建错误。
- 页面数据请求未增加登录依赖；昵称与头像只在全局已有本人资料时显示，否则安全回退为“搭子”和受控默认头像。

请重点审查：

1. 与 Concept A 的尺寸比例、负边距堆叠、阴影透明度、信息层级是否合理；指出准确选择器和最小 rpx 修改。
2. 375px 与 320px 下是否存在文字挤压、三卡破框、右上胶囊触控不足、Hero 空槽误解或活动首屏节奏问题。
3. 三条游标追加逻辑是否有并发、旧请求覆盖、重复活动、失败锁不释放或终点文案状态错误。
4. WXML 的可访问性语义、按钮/不可点击占位区分、空图片条件渲染是否稳健。
5. 不要建议现在填充 Hero 或快捷卡图片；图片资产会由用户下一步提供。
6. 不要建议恢复“成团记忆”、虚构邻里动态、天气、图片帖子或统计数据。

OUTPUT:

- 先给总体判断与最主要问题。
- 按 Critical / Warning / Info 分级。
- 每项必须写清：文件或选择器、触发条件、用户影响、最小修改建议。
- 单独列出“已被代码与开发者工具证实”和“必须真机验证”的边界。
- 最后明确写“可以交付 / 修复后交付 / 不可交付”。
