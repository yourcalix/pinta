# Gemini Web Analysis Prompt

ROLE: frontend UI/UX analyzer and reviewer

PROJECT:
“拼吧”微信原生小程序，面向澳门校园与附近用户，提供拼同行、拼运动、拼饭桌活动发布和组队。品牌是暖米白生活方式首页、手绘插画、黑色主要操作与绿色品牌强调色。用户希望接入高德地图，让新发布活动能被附近用户发现。

REVIEW TARGET:
这是实现前的信息架构与交互分析。当前首页有三张快捷卡：“组队拼团 / 琐碎回忆 / 暂定”，下方是最多 3 条活动预览和右侧“发现更多”。目前“组队拼团”只滚动到首页活动区；“发现更多”进入完整的全部活动列表页。计划调整为：

- “组队拼团”直接进入现有全部活动列表页，保留关键词、活动类型筛选、游标分页、加载/空态/错误态。
- “发现更多”进入新增的“附近拼吧”页面，只显示有真实会合地点坐标且处在选定半径内的活动。
- 首页首屏不请求定位；首页现有 3 条卡片改称全城“正在组队”预览，避免未定位却声称“附近”。
- 新“附近拼吧”页在用户明确操作后获取当前定位；拒绝定位时提供说明、重试和“查看全部活动”降级入口。
- 附近结果按服务端真实距离排序，每张活动卡增加如“距你 860m / 2.4km”的真实距离标签。
- 初版建议采用列表优先，不把活动精确坐标返回客户端；高德主要用于发布时的 POI 搜索、选点和逆地理编码。如果采用地图标记视图，才需要额外公开发布者主动选择的公共场所坐标。
- 三类发布表单均新增“公开会合地点”：拼同行是出发集合点，拼运动是场馆，拼饭桌是餐厅。必须明确提示“这是活动公开地点，不会保存你的实时位置”。
- 高德不可用、Key 未配置、无搜索结果、网络失败和定位拒绝都要有可理解的降级状态。

KNOWN CONSTRAINTS:

- 微信原生小程序，无前端框架；首页为固定单屏，不能继续塞入大型地图或长列表。
- 不在首页首屏调用定位，不把查看者当前位置存入用户资料、本地缓存、活动、日志或审计；查看者坐标只作为一次附近查询的临时参数。
- 新活动保存的是发布者主动选择并公开的活动会合地点，不是个人实时位置；历史无坐标活动继续出现在全部活动页，但不进入附近列表。
- 服务端新增独立 `activity.nearby`，执行半径过滤和距离排序；不能在前端拉取全部活动后自行算距离。
- 坐标统一使用 GCJ-02。高德负责 POI 选点/逆地理编码，CloudBase 负责应用自己的活动数据和 GeoPoint 地理索引。
- 默认附近半径建议 3km，可选 1km / 3km / 5km / 10km，服务端最大 10km。
- 当前页面视觉最低正文 28rpx、辅助文字 24rpx、热区约 44px，必须适配 320px、Safe Area、大字模式、弱网和原生授权弹窗。
- “帖子”在本需求中是活动卡，不是社区帖；点击仍进入现有活动详情。
- 不得修改“琐碎回忆”、发现社区、消息、我的或三类发布表单的其他业务字段和视觉分支。
- 高德 Key 不硬编码；实际上线前需要配置 request 合法域名和 CloudBase 地理索引。

REVIEW QUESTIONS:

1. 上述入口重分工是否清晰：“组队拼团 = 全部活动”，“发现更多 = 附近活动”？首页“附近拼吧”是否应改名为“正在组队”？
2. 新附近页应采用哪种首版结构：A. 列表优先（推荐，距离标签 + 半径筛选）；B. 地图上半屏 + 活动列表下半屏？请从隐私、理解成本、性能和“接入高德”的用户预期判断。
3. 定位授权应在进入附近页后自动触发，还是先显示说明和“查看附近活动”按钮再触发？请给出推荐流程。
4. 定位拒绝、定位失败、附近为空、服务不可用、地理索引未部署时，各状态应如何布局和写文案？
5. 三类发布表单的“公开会合地点”应该放在哪一张卡、如何表示已选 POI、如何允许修改，以及怎样清晰区别活动地点与个人实时位置？
6. 为兑现“每次发布后附近人可见”，会合地点应强制选择，还是允许手动文字发布但不进入附近？请指出用户体验和数据完整性的取舍并给出推荐。
7. 1/3/5/10km 半径 Chip、距离标签、类型筛选如何与现有活动列表视觉保持一致？
8. 检查 320px、大字、Safe Area、原生地图层级、授权弹窗、滚动和返回行为的风险。
9. 列出必须保留的无障碍语义，包括定位按钮、距离、地图标记（如有）和错误态。

OUTPUT:
1. 总体判断与最主要问题
2. Critical / Warning / Info 分级问题清单
3. 每个问题的具体修改建议及理由
4. 推荐的最终页面层级与逐状态交互流程
5. 三类发布表单的会合地点控件规范
6. 可选布局或视觉方案（仅在确有价值时提供）
7. 需要产品负责人决定的问题
8. Verdict：APPROVE_PLAN 或 REQUEST_CHANGES

Do not assume missing business facts. Separate objective usability issues from subjective visual preferences. Do not output implementation code.
