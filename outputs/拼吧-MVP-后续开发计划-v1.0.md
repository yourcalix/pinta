# 拼吧 MVP 后续开发计划 v1.0

状态：CCG 综合定稿

日期：2026-08-23

适用基线：代码级最小 MVP 已完成，Mock 模式、CloudBase 聚合云函数、23 项自动化测试和核心页面视觉验收均已通过；尚未接入真实 AppID、生产 CloudBase 环境或完成微信审核。

## 1. 执行结论

后续开发不应立即扩张功能，而应先把“本地可运行 MVP”推进为“真实多人可用、可审核、可监控、可处置”的小规模上线版本。推荐顺序如下：

1. **上线准备 P0**：真实 AppID、测试/生产云环境、集合与索引、服务端权限、内容安全、隐私与类目材料；同步完成当前实际使用隐私能力的授权回调与拒绝降级。
2. **真实闭环 P0**：使用 3 个真实微信账号完成跨账号发布、申请、批准、成团、联系信息解锁、退出/取消和举报；将分享卡片冷启动落地纳入同一轮验证。
3. **运营闭环 P0**：补齐举报列表与处置、活动下架、账号受限前端兜底、订阅消息直达、审计记录、日志告警和数据库恢复演练。
4. **单城灰度**：默认先以上海单城、小规模受邀用户运行，不同时开放多城市和大流量入口。
5. **V1.1 履约增强**：严格按“发布草稿 → 分页与状态一致性 → 公开问答 → 最小筛选”推进，不做即时聊天或高级联合筛选。
6. **V1.2 信任与数据**：建设爽约/取消原因、用户限制、运营指标和数据治理，不急于引入复杂信用分。
7. **继续冻结**：支付/担保、地图与精确定位、二维码、即时聊天、司机招揽、外部商品链接和复杂推荐。

## 2. 当前基线与主要缺口

### 2.1 已具备

- 游客浏览，三类活动（拼车、拼商品、拼搭子）发布与筛选。
- 两步发布、申请、发起者批准即占位、达到人数自动成团。
- 服务端幂等、最后名额原子控制、角色权限和公开 DTO 脱敏。
- 成团后有效成员通过独立鉴权接口查看必要联系信息。
- 取消、完成、撤回、退团、站内通知、举报和活动下架动作。
- Mock/CloudBase 服务边界、内容安全适配入口、审计与自动化测试。

### 2.2 上线缺口

- 当前仍使用 `touristappid`、`useMock=true`，未连接真实微信身份和生产数据。
- 8 个集合、生产索引和“客户端不可直接读写”规则尚需在云端落地。
- 内容安全能力、订阅消息模板、隐私保护指引、服务类目和审核材料依赖真实账号配置。
- 尚未完成 2—3 个真实账号的并发、权限、拒绝授权、弱网与真机测试。
- 尚未验证微信聊天分享卡片的冷启动路由、订阅消息目标页面和跨账号返回后的数据刷新。
- 举报已有提交与活动下架能力，但缺少最小运营侧举报列表、处理结果和用户限制闭环。
- 活动下架和账号受限目前缺少稳定领域错误码及用户可理解的前端兜底状态。
- 需要建立可检索日志、错误告警、资源用量观察和数据库恢复演练。

| G2 多账号闭环 | 证明核心业务在真实身份、分享冷启动与并发下成立 | 真机用例、分享落地、并发/幂等/越权结果、缺陷清单 | P0 用例 100% 通过 | 2—3 人日 |
| G3 安全运营闭环 | 能触达、发现、恢复和处置线上问题 | 订阅直达、下架/受限兜底、举报处置、日志告警、恢复演练 | 无 Critical，通知与举报均可闭环 | 2—4 人日 |

## 4. G0：决策与账号准备

### 4.1 产品默认决策

为避免阻塞，计划采用以下默认值，用户可在进入 G1 前修改：

- **灰度地域**：上海单城；公开地点仍只到区和商圈/公共会合点。
- **灰度人群**：受邀小规模用户，暂不投放公域流量。
- **运营角色**：首发 1 名超级管理员；所有处置动作写入审计日志。
- **举报服务目标**：24 小时内首次响应，72 小时内给出处理结果；人身安全或诈骗风险优先处置。
- **通知优先级**：新申请、申请结果/成团、取消/下架；用户拒绝订阅时只保留站内通知，不阻断业务。
- **首发运营能力**：举报列表、举报处理、活动下架、必要的用户限制；不开发完整 CMS。

### 4.2 账号与材料清单

- 真实小程序 AppID、管理员及开发者权限。
- 确认小程序服务类目、名称和简介是否允许当前三类信息撮合场景。
- 创建 CloudBase 测试环境与生产环境；记录环境 ID，但不把密钥写入仓库。
- 配置《用户协议》《隐私保护指引》、信息收集用途、联系方式披露规则与举报渠道。
- 盘点实际调用的隐私相关接口，仅为已使用能力声明用途；当前不使用手机号授权，不为未来功能提前索权。
- 申请订阅消息模板；模板未获批时允许站内通知降级上线。
- 确认微信内容安全接口权限及生产调用方式。

### 4.3 隐私授权前端门禁

- 按当前微信基础库和隐私规则接入隐私授权回调（包括适用时的 `wx.onNeedPrivacyAuthorization`）及统一隐私弹窗。
- 当前重点覆盖成团页复制联系方式等实际使用的隐私相关能力；请求前解释用途，拒绝后只中止本次敏感操作，不阻断浏览和其他非敏感流程。
- 不增加手机号授权、通讯录、精确位置或用户画像读取；路线图中的隐私适配不能成为扩大收集范围的理由。
- 授权弹窗内容、隐私指引声明和真实 API 调用保持一致。

### 4.4 验收

- 账号所有权、开发权限、环境和合规材料均有明确负责人。
- 测试与生产环境隔离，配置表中没有真实密钥进入 Git。
- 类目或审核结论若限制某一场景，先关闭对应类型入口，不通过改文案规避审核。
- 首次使用受隐私规则约束的能力时能完成授权；拒绝后不执行该能力，也不出现白屏、循环弹窗或强制退出。

## 5. G1：真实 CloudBase 环境接入

### 5.1 配置与部署

- 将 `project.config.json` 的 AppID 替换为真实值。
- 将环境差异集中在配置层：测试环境、生产环境、`cloudEnv`、`useMock`、订阅模板 ID。
- 测试/生产联调时设置 `useMock=false`；保留 Mock 作为本地演示和自动化测试能力。
- 部署 `cloudfunctions/api`，生产环境至少配置：
  - `PINBA_ENV=production`
  - `ENABLE_WECHAT_CONTENT_CHECK=true`
- 生产环境在内容安全能力不可用时保持 fail-closed：拒绝新增 UGC，不能静默放行。

### 5.2 数据库

创建以下集合：

- `users`
- `activities`
- `applications`
- `members`
- `notifications`
- `reports`
- `auditLogs`
- `idempotency`

所有业务集合设为客户端不可直接读写，只允许聚合云函数访问。建议索引：

| 集合 | 索引 |
| --- | --- |
| `activities` | `status + startsAt`；`type + status + startsAt`；`city + district + status + startsAt`；`ownerId + updatedAt` |
| `applications` | `activityId + createdAt`；`activityId + applicantId + status` |
| `members` | `activityId + userId + status`；`userId + role + status` |
| `notifications` | `userId + createdAt`；`userId + type` |
| `reports` | `status + createdAt`；`reporterId + targetType + targetId` |
| `auditLogs` | `targetType + targetId + createdAt`；`actorId + at` |

### 5.3 安全检查

- 身份只取云函数可信上下文，不接受客户端传入用户 ID 作为授权依据。
- 公开列表/详情持续使用脱敏 DTO；OpenID、手机号和联系方式不进入公开响应。
- 联系方式接口继续校验活动已成团且请求者为有效成员。
- 写操作保留幂等键；批准最后一个名额继续使用事务/原子更新。
- 为发布、申请、举报、管理动作配置合理限频和结构化错误日志。

### 5.4 验收门槛

- 测试环境完成一次空库初始化、云函数部署、真实登录和完整数据写入。
- 直接从小程序端读取/写入任一业务集合均被拒绝。
- 内容安全成功、违规、超时和不可用四种路径均有明确结果。
- 冷启动、普通请求和错误请求日志可通过 requestId 定位。

## 6. G2：真实多账号与真机闭环

### 6.1 账号矩阵

至少准备 3 个真实微信账号：发起者 A、申请者 B、申请者 C；如运营账号与普通账号分离，再增加管理员 D。

### 6.2 必测场景

1. A 发布拼车、拼商品、拼搭子各一条，B/C 能在真实数据中发现并申请。
2. A 批准 B 后立即占位；达到目标人数时自动成团，不出现参与者二次确认。
3. B/C 未成团前不能获得联系方式；成团后仅有效成员能解锁必要信息。
4. B/C 并发争抢最后一个名额，最终人数不超员，失败方得到可理解提示。
5. 快速重复点击发布、申请、批准不会产生重复活动、申请或成员记录。
6. 被拒绝、主动撤回或已退团的用户在仍招募时可重新申请。
7. 取消、完成、退出、过期、已满、下架状态在所有入口显示一致。
8. 普通用户调用管理员动作、非发起者审批、非成员读取联系信息均被拒绝。
9. 拒绝隐私/订阅授权、断网、8 秒超时、前后台切换和重复返回均不造成卡死。
10. iOS/Android 各至少一台真机验证大字号、软键盘、安全区和横向分类手势。
11. 详情页实现 `onShareAppMessage`，分享路径携带活动 ID；在小程序未启动时从微信聊天卡片进入，等待全局初始化完成后再加载公开详情。
12. 分享冷启动对游客保持可浏览，只有申请/发布等写操作才触发最小登录；无效、过期或已下架 ID 进入受控兜底页。

### 6.3 验收门槛

- 核心业务与安全用例通过率 100%，Critical 为 0。
- 所有失败均能恢复或重试，不要求用户卸载/清数据。
- 用例保留账号角色、前置数据、操作步骤和证据，形成可重复回归清单。
- 微信聊天分享卡片在冷启动、热启动、已登录和游客四种状态下均能落到正确活动，且不会误用上一个 Mock/真实账号上下文。

## 7. G3：安全、运营与可恢复性

### 7.1 最小举报处置闭环

现有 `report.create` 和 `admin.activity.suspend` 基础上，补齐兼容动作：

- `admin.report.list`：按状态和时间查看举报。
- `admin.report.resolve`：记录处理结论、原因、操作人和时间。
- `admin.user.restrict`：仅对明确违规用户设置有限期/永久限制；首发可只支持禁止发布与申请。
- 保留 `admin.activity.suspend`，下架后相关用户收到站内通知。

管理入口采用独立内部页面或内部工具，必须做服务端管理员鉴权，不能仅靠“隐藏入口”。所有读写管理动作写入 `auditLogs`。

前后端约定稳定的受控结果：活动被运营下架时返回可识别的“活动不可用/已处理”领域状态，账号受限时返回受限类型、可执行动作和必要提示。页面统一展示不可操作卡片，禁止把底层 `FORBIDDEN`、`NOT_FOUND` 或 JSON 异常直接暴露给用户。

### 7.2 订阅与站内通知

- 在用户发布或申请等明确点击动作之后请求订阅，不在冷启动时索取授权。
- 首发事件：新申请、申请批准/成团、活动取消或下架。
- 用户拒绝、模板未配置或发送失败时，不影响主链路；站内通知仍是事实来源。
- 服务端发送订阅消息时写入明确目标页面及活动 ID：新申请落到申请管理页，批准/成团落到成团页，取消/下架落到受控详情页。
- 目标页面在冷启动时自行解析查询参数，并等待全局 CloudBase/用户初始化 Promise 后取数；`App.onShow` 只做启动参数校验或恢复辅助，不把它设计成并不存在的“模板消息监听器”。
- 记录“请求、接受/拒绝、发送成功/失败”的聚合指标，不存储无关隐私信息。

### 7.3 日志、告警与恢复

- 结构化日志最少包含：requestId、action、actor 哈希/内部 ID、结果码、耗时、环境；禁止输出联系方式和正文 UGC。
- 告警优先覆盖：云函数错误率、内容安全连续失败、数据库错误、请求耗时、异常流量和资源配额。
- 建立每日检查和故障处理卡：影响范围、临时止损、回滚、数据修复、用户通知。
- 做一次数据库回档演练。CloudBase 文档型数据库目前由系统每日自动备份，默认保留 7 天；回档会生成新集合，因此必须验证“回档 → 校验 → 切换/迁移”的完整步骤，而不是把回档等同于原地覆盖。
- 上线前核对当前套餐的日志、告警、回档、QPS 和存储配额，避免把控制台能力视为无限免费资源。

### 7.4 验收门槛

- 从提交举报到处理、下架/限制、通知和审计记录能完整演示。
- 点击微信服务通知能直达正确活动上下文；无权限、活动已处理或账号受限时进入对应兜底状态。
- 能通过 requestId 在 10 分钟内定位一次模拟错误。
- 至少一条关键告警能真实触发并到达负责人。
- 回档演练有步骤、耗时、数据校验与失败回退记录。

## 8. G4：单城灰度上线

### 8.1 发布策略

- 默认上海单城、受邀用户、小流量，不购买投放。
- 首批重点验证三种类型是否都产生真实供需；如果某一类型带来明显合规或举报压力，可用配置临时关闭。
- 每次发布使用版本号、变更说明、数据库兼容说明和明确回滚点。
- 灰度期间不同时上线多项 P1 功能，保持问题可归因。

### 8.2 上线门禁

- 自动化测试、静态检查、真实账号回归全部通过。
- 微信审核材料、隐私指引、用户协议、举报入口和联系方式披露说明一致。
- 内容安全、管理员、告警、恢复和用户支持负责人均可用。
- 无 Critical；未修 Warning 有明确接受理由、负责人和截止条件。

### 8.3 灰度观测指标

核心漏斗：

- 浏览用户 → 发布/申请动作转化。
- 发布成功率、申请成功率、批准率、成团率、完成率。
- 首次申请耗时、成团耗时、联系信息解锁率。

健康与风险：

- 取消率、撤回率、批准后退团率、过期率、举报率。
- API 成功率、P95 耗时、超时率、内容安全失败率。
- 订阅请求接受率、发送成功率、站内通知读取率。

指标按日看趋势，不在样本很小时设置虚假精确 KPI。首轮更看重是否出现不可接受的安全问题、是否有人真实成团、失败原因能否解释。

### 8.4 暂停/回滚条件

- 联系方式越权、超员、跨用户数据泄露或管理员鉴权失效：立即停止新写入或回滚。
- 内容安全持续不可用：按 fail-closed 保持发布/申请受限，并在页面说明服务异常。
- 严重人身安全、诈骗或违法内容事件：下架相关活动、保全审计记录并人工处理。

## 9. V1.1：履约与沟通增强

V1.1 只解决灰度数据证明存在的问题，推荐优先级如下：

### 优先级 1：发布草稿本地恢复

- 本地保存两步发布草稿，记录版本和更新时间；发布成功后立即清理。
- 再次进入时允许继续或丢弃，账号切换时不得加载其他用户草稿。
- 只保留有限时间，联系方式等字段按最小化原则处理，避免长期残留。

验收：误触返回、切后台或进程被回收后可以恢复；发布成功、主动丢弃或过期后不再恢复。

### 优先级 2：分页与状态一致性

- 发现页使用稳定游标/分页，默认页大小从真实数据压测后确定，不把 `10` 写成不可配置规则。
- 补齐加载更多、无更多、刷新、重复请求和弱网重试，防止卡片重复或漏项。
- 自动处理报名截止和活动过期，统一列表、详情、“我的”和通知状态。
- G2/G3 已完成的分享与订阅直达继续作为回归项，不再列为 V1.1 新功能。

验收：数据量增长后列表不重复/漏项；前端时间到期后立即变为不可申请，并最终与服务端状态一致。

### 优先级 3：公开问答，而非即时聊天

- 在活动详情增加公开问答，解决时间、地点、规则等高频疑问。
- 问题和回复都经过内容安全、限频和举报；联系方式、二维码、外链默认拦截。
- 发起者可回复，提问者可删除自己的未回复问题；不做私聊和已读状态。

验收：问答公开可审计，不成为绕过“成团后才解锁联系方式”的通道。

### 优先级 4：最小筛选

- 在现有类型 Tab 基础上，只增加单选区域和必要的时间/招募状态筛选；是否增加关键词搜索由灰度数据决定。
- 不做费用区间、强度、多选标签等高级联合筛选，不做个性化推荐。

验收：筛选可清空、可恢复默认值，与分页组合时不串数据；活动量不足时允许整项不开发。

### 明确可砍项

- 高级多条件联合筛选。
- 未经灰度数据证明的关键词搜索、常用地点和模板复用。
- 活动临近提醒等额外订阅场景；G3 首发通知已足够时不扩张消息频率。

## 10. V1.2：信任、运营与数据治理

### P1-E 履约信号

- 完成/取消/退团时收集结构化原因，允许补充短文本。
- 记录爽约或异常事件，但先作为运营信号，不直接公开复杂信用分。
- 只有样本量、申诉流程和误伤控制成熟后，才评估对外信誉标签。

### P1-F 运营效率

- 举报筛选、批量查看上下文、处置模板、用户限制到期自动解除。
- 对高频发布、重复文本、异常申请等建立规则告警，先人工确认再处置。
- 管理员权限最小化；若运营人数增加，再拆分审核员与超级管理员。

### P1-G 数据治理

- 建立事件字典和版本，保证发布、申请、批准、成团、完成、取消、举报等口径一致。
- 明确数据保留、删除和导出流程，定期检查过期幂等记录、通知与审计存储量。
- 周报聚焦供需、漏斗、履约和安全，不以停留时长作为首要成功指标。

## 11. P2 停车场：没有证据前不进入开发

- 平台支付、保证金、退款、资金担保。
- 地图、精确定位、实时轨迹或距离排序。
- 二维码上传/识别、公开微信号或手机号。
- 即时聊天、群聊、语音、已读回执。
- 司机/车主招揽、车辆服务、运输承诺。
- 外部商品链接、代购、平台代理下单。
- 复杂信用分、黑盒推荐、多城市同时扩张。
- UGC 图片；只有文本场景跑通且运营有能力做图片审核时再评估。

## 12. 建议执行顺序与交付物

每个工作包完成后都执行：测试 → CCG 后端/前端分域审查 → 修复 Critical/Warning → 真机证据 → 归档。

1. **工作包 1：生产与隐私基线**
   交付：环境配置说明、集合/索引/权限截图或记录、云函数部署记录、内容安全结果、隐私授权与拒绝降级证据。
2. **工作包 2：多账号回归**
   交付：真实账号测试矩阵、微信分享冷/热启动、并发与越权测试、缺陷及修复记录。
3. **工作包 3：运营与可恢复性**
   交付：举报处置能力、下架/账号受限兜底、订阅直达、管理员鉴权测试、告警记录、数据库回档演练。
4. **工作包 4：灰度上线**
   交付：审核包、版本清单、回滚方案、灰度日报/周报模板。
5. **工作包 5：V1.1 单主题迭代**
   每次只选择通知、问答、发现或草稿中的一个主题，按数据验证后再推进下一个。

## 13. 进入开发前需要用户确认的 5 项

以下选择会影响真实配置和开发范围；本计划已给出推荐默认值：

1. **城市与定位**：默认上海单城、首页手动选择城市，不请求设备 GPS；是否确认。
2. **拼车费用**：默认只保留“免费互助”和“油费/高速费 AA”，停车费可写在规则中，不新增费用枚举；是否确认。
3. **线下纠纷边界**：默认平台只提供举报、下架和账号限制，不介入线下转账仲裁或赔付；是否确认。
4. **操作频控**：灰度首周先记录取消/撤回频率并保留服务端限流能力，不立即采用“取消 3 次、撤回 5 次”等未经数据验证的硬阈值；出现滥用后再按数据启用，是否确认。
5. **上线降级**：默认订阅模板未获批时允许站内通知降级，但分享卡片、隐私适配和举报处置不可降级；是否确认。
