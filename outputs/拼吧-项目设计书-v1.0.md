# “拼吧”微信小程序项目设计书（MVP 实施基线 v1.0）

> 文档状态：CCG 前后端分析已完成，作为 MVP 实施基线  
> 版本：1.0  
> 日期：2026-08-23  
> 结论来源：用户需求、GPT 5.3 Codex Spark 后端分析、网页版 Gemini 3.6 前端分析、微信/腾讯云官方文档核验、GPT 5.6 Sol 主会话综合

## 1. 执行摘要

“拼吧”是一款帮助用户临时找到同行者、共同购买者和活动搭子的微信小程序。它首先解决的是“组织一个小型共同活动太麻烦”的问题，而不是建设综合商城、网约车平台或陌生人社交平台。

MVP 的核心闭环为：

`发现/发布 → 查看详情 → 申请加入（同意获批后自动占位）→ 发起者审核 → 达到人数自动成团 → 解锁必要联系信息 → 完成/取消 → 举报`

首版提供三个清晰入口，但共用一套“拼活动”底座：

- 拼车：同路线出行者共同约车或结伴出行；平台不提供车辆，不允许用户以司机身份经营载客。
- 拼商品：多人协同凑数量或优惠；平台不收款、不担保商品和履约。
- 拼搭子：围绕具体兴趣或活动组队；不做婚恋、不做无限制陌生人交友。

建议首发采用“微信原生小程序 + CloudBase 云函数 + 文档数据库”的最短验证路径。所有业务写入通过服务层/云函数，避免页面直接依赖数据库结构，为以后迁移到独立后端保留边界。

## 2. 文档中的结论级别

- **实施决定**：CCG 已交叉验证并纳入 MVP 范围；用户仍可在实现中提出变更。
- **暂定假设**：为保证项目可继续而采用的默认值，可在审核时修改。
- **待外部验证**：需要微信提审、主体资质或真实用户测试才能确认。

## 3. 产品定位与边界

### 3.1 一句话定位

在微信内快速发起和加入一场小型共同活动，让“找人、凑数、确认、成团”形成可追踪的闭环。

### 3.2 核心价值

- 对发起者：用结构化表单代替群聊里反复统计和确认。
- 对参与者：按城市、时间、类型和条件快速找到合适的拼局。
- 对双方：通过申请、确认、成团和举报机制降低临时放鸽子及隐私暴露。

### 3.3 MVP 明确不做

- 不自营车辆、司机、运输或配送。
- 不代收商品款、车费，不做担保交易、分账或退款。
- 不做即时聊天、群聊和朋友圈式内容流。
- 不做婚恋、约会、陪玩交易或未成年人社交。
- 不做全国规模化运营承诺、复杂信用分和推荐算法。
- 不承诺商品质量、人身安全或线下履约结果。

## 4. 目标用户与场景

### 4.1 目标用户

- 18 岁及以上、经常在校园周边/产业园/社区/同城区域活动的微信用户。
- 有明确时间、地点、人数或预算约束，希望临时找到一到数名同伴。
- 发起者愿意对申请者做最小筛选；参与者在申请时明确同意“获批后自动加入并占用名额”。

### 4.2 典型任务

1. 下班后从园区到机场，希望找到同路线用户共同预约合规车辆。
2. 想购买一箱商品，但单人数量过多，希望找到同区域用户分摊数量。
3. 周末想打羽毛球、看展或徒步，希望找到时间合适的活动搭子。

### 4.3 冷启动策略

- 暂定单城市、单社区或单园区试点。
- 允许运营人员创建带“官方组织”标识的真实活动，不制造虚假用户和虚假参与人数。
- 首页默认展示近期、可加入、信息完整的活动；无数据时突出发布入口和示例模板。
- 首轮验证优先关注成团率、完成率和举报率，不追求页面停留时长。

## 5. MVP 功能范围

### 5.1 P0：必须完成

- 列表和详情支持零登录浏览；发布、申请和“我的”按动作触发微信登录与服务端业务会话。
- 最小用户资料：昵称、头像（可选）、所在城市、兴趣标签、成年确认。
- 三类活动的创建、草稿、发布、详情、筛选和搜索。
- 申请加入、发起者批准/拒绝、批准后自动占位、参与者撤回/退团。
- 名额并发控制、自动成团、截止过期、发起者取消、完成确认。
- 我的发布、我的参与、待办状态和站内通知。
- 成团后向有效成员展示最小必要的会合/联系信息；信息通过独立鉴权接口按需返回。
- 文本内容安全、发布频控、举报、运营侧下架/封禁、审计记录。
- 隐私指引、用途说明、授权拒绝后的降级路径。
- 站内通知和可配置的微信订阅消息适配器；未配置模板时自动降级为站内通知。

### 5.2 P1：MVP 后优先

- 图片上传与异步内容审核。
- 地图选点、模糊位置和距离排序。
- 公开问答/站内私信、结构化评价、申诉复核、爽约规则和更完整的信誉展示。

### 5.3 P2：验证后再评估

- 微信支付、担保、分账、退款和保险。
- 智能推荐、路线匹配、复杂搜索和信用分。
- 商家、车队、俱乐部等组织账号和商业化工具。

## 6. 信息架构与页面清单

### 6.1 底部导航（实施决定）

1. **发现**：推荐/最新活动、类型切换、城市和条件筛选。
2. **发布**：居中主操作，先选类型再填写表单。
3. **我的**：待处理、我的发布、我的参与、资料、安全与规则。

“消息”不单独占一个 Tab，MVP 作为“我的”中的待办/通知入口，减少空页面和导航复杂度。

### 6.2 页面清单

| 页面 | 主要目标 | 关键状态 |
| --- | --- | --- |
| 首次进入/登录 | 浏览免登录；在发布/申请时完成最小登录 | 游客、登录中、失败、隐私未同意 |
| 发现首页 | 找到可加入的活动 | 加载、空、筛选无结果、失败 |
| 筛选/搜索 | 缩小类型、城市、时间和状态 | 已选条件、重置、无结果 |
| 活动详情 | 判断是否适合并申请 | 可申请、已申请、满员、已截止、本人发布 |
| 选择发布类型 | 进入三类表单 | 拼车、拼商品、拼搭子 |
| 发布/编辑 | 生成结构化活动 | 草稿、校验失败、内容受限、提交中 |
| 申请确认 | 补充一句申请说明 | 可提交、重复、频繁、已满 |
| 申请管理 | 发起者处理申请 | 待处理、已批准、拒绝、撤回、名额已满 |
| 成团页 | 展示成员和必要联系信息 | 未成团、已成团、取消、完成、无权访问 |
| 我的发布/参与 | 查看进行中和历史记录 | 待办、进行中、已结束 |
| 通知中心 | 汇总状态变化和操作入口 | 未读、已读、空 |
| 完成/取消 | 确认结果并说明原因 | 成功、取消、争议 |
| 举报 | 结构化安全反馈 | 可举报、已提交、重复举报、处理中 |
| 个人资料/设置 | 管理最小画像和隐私入口 | 完整、不完整、受限 |

### 6.3 关键交互基线

- 三类场景共用卡片骨架：状态、标题、时间、区域、人数进度和主操作；中部使用路线、商品缺口或活动强度等场景槽位。
- 发布采用两步表单：第一步填写决定匹配的时间、区域/商品和人数；第二步填写规则、安全承诺与成团后联系方式。
- 表单切换或意外退出时保留一个本地草稿；提交失败不得清空，错误必须定位到字段。
- “我的”是协同中心，顶部优先展示待审批、已成团和即将开始的任务卡片。
- 页面覆盖骨架、空数据、筛选无结果、弱网、重试、满员、过期、取消和下架状态。

## 7. 三类活动字段

### 7.1 通用字段

- 类型、标题、简短描述。
- 城市、行政区/商圈、公开地点描述。
- 开始时间、截止时间、目标人数（2—20 人；MVP 中即容量上限）。
- 参与条件、发起者补充规则。
- 仅成团成员可见的会合说明或联系方式。

### 7.2 拼车扩展

- 出发区域、到达区域、出发时间、可接受时间浮动。
- 当前人数、需要人数、行李说明、费用分摊模式。
- 费用分摊模式只允许：`FREE`（免费互助）、`SHARED_COST`（合理成本均摊）、`NO_COST`（不涉及费用）；禁止填写具体收费金额或司机报价。
- 固定安全提示：仅限同行者共同约用合规交通工具，不得以司机身份招揽载客。
- MVP 不公开精确门牌和完整轨迹。

### 7.3 拼商品扩展

- 商品名称、规格、目标总量、当前缺口、预估单价区间。
- 购买渠道文本、分配/自提方式、预计到货时间。
- 固定风险提示：平台不收款、不担保商品、支付与交付由成员自行判断。
- MVP 不提供外部跳转链接、平台收款和自动分账。

### 7.4 拼搭子扩展

- 活动类别、强度/水平、活动时长、费用方式、装备要求。
- 可选年龄段偏好不得替代成年门槛，不允许性暗示或婚恋招募。
- 线下活动显示公共场所见面和告知亲友的安全提示。

## 8. 核心流程与规则

### 8.1 发布流程

1. 选择类型。
2. 填写通用字段与类型扩展字段。
3. 客户端即时校验必填、时间和人数。
4. 服务端校验身份、频率、业务规则和文本安全。
5. 发布成功进入招募状态；失败返回可操作的原因，不丢失草稿。

### 8.2 参与与成团流程

1. 用户提交申请；每个用户对每个活动仅允许一条有效申请，提交前明确展示“获批后自动加入并占用名额”。
2. 发起者批准或拒绝。
3. 批准操作在事务内直接占用名额；并发争抢最后名额只能有一个成功。
4. 成员数达到目标人数时自动成团并停止公开招募。
5. 成团后仅向有效成员开放最小必要的联系/会合信息；首次查看需确认安全提示。
6. 到达活动时间后可标记进行中；结束后由发起者完成，参与者可提交异议。

### 8.3 取消与退出

- 申请获批前可撤回；获批后在锁定时间前可退团并释放名额，临近开始退出记录原因和风险事件。
- 成团前发起者可取消并通知所有有效申请者。
- 成团后取消必须选择原因，写入审计并触发成员通知。
- 爽约与降权在 MVP 只记录事件，不展示未经验证的公开信用分。

### 8.4 已发布内容修改

- 可修改：补充描述、公开地点说明、非核心注意事项。
- 需重新确认或禁止直接修改：活动类型、开始时间、出发/到达区域、价格/费用核心条件、目标人数。
- 核心条件变化建议采用“取消并重新发布”，避免参与者在不知情下被改变约定。

## 9. 状态机

### 9.1 活动状态

`DRAFT → RECRUITING → FORMED → IN_PROGRESS → COMPLETED`

旁路终态：`CANCELLED`、`EXPIRED`；治理状态：`SUSPENDED`。

### 9.2 申请状态

`PENDING → APPROVED`

旁路终态：`REJECTED`、`WITHDRAWN`、`LEFT`、`EXPIRED`、`CANCELLED_BY_ACTIVITY`。

### 9.3 举报状态

`NEW → TRIAGED → INVESTIGATING → RESOLVED → CLOSED`

MVP 可合并部分运营步骤，但数据字段保留处理人、原因、证据摘要、处置和时间。

## 10. 信任、安全、隐私与治理

### 10.1 MVP 默认规则

- 暂定仅允许 18 岁及以上用户发布和参加活动。
- 新账号设置每日发布/申请上限；异常高频返回明确冷却时间。
- 标题、描述、申请说明、取消原因和举报文本在写入前执行内容安全检查。
- 联系方式、精确地点和成员信息不进入公开列表及公开详情。
- 举报入口在详情、成员和历史记录中保持可达。
- 运营人员可下架活动、限制用户、解除限制并留下不可覆盖的审计记录。

### 10.2 授权最小化

- 首次打开允许直接浏览，不要求登录，也不主动索要位置、头像、手机号等权限。
- 城市可手动选择；精确位置不是 MVP 必需能力。
- 只有在用户主动使用需要隐私能力的功能时才解释用途并请求授权。
- 用户拒绝后提供手动填写或不启用该能力的路径。
- MVP 不要求手机号；微信号文本仅用于成团后的成员联系，不在公开 DTO 中返回。

### 10.3 免责声明边界

免责声明不能替代产品控制。页面文案应明确平台是信息撮合工具，同时通过延迟解锁、内容审核、举报、限流和运营处置降低风险。

## 11. 技术架构建议

### 11.1 MVP 选型

- 前端：微信原生小程序，TypeScript（若开发者工具与构建配置允许）或严格模块化 JavaScript。
- 后端：CloudBase 云函数，Node.js 运行时。
- 数据：CloudBase 文档数据库；写操作仅通过云函数执行。
- 文件：MVP 默认使用类型图标和纯文本；图片进入 P1 后接云存储与异步安全审核。
- 通知：站内通知 P0；微信订阅消息适配器 P0，只在用户操作触发点按需申请订阅，缺少模板配置时安全降级。

### 11.2 逻辑分层

```text
小程序页面/组件
  ↓
前端 services（统一调用契约）
  ↓
云函数 BFF/API
  ├─ 身份与权限
  ├─ 活动与类型规则
  ├─ 申请/成团状态机
  ├─ 通知
  ├─ 内容安全与举报
  └─ 审计
  ↓
CloudBase 数据库/存储/微信开放接口
```

### 11.3 为什么暂选 CloudBase

- 小程序可原生调用云函数并自动携带身份，减少 MVP 登录和部署工作量。
- 云函数、数据库、存储和权限能力在一个平台内，适合单城市验证。
- 通过前端 `services` 和云函数领域层隔离数据库调用，可降低未来迁移成本。

### 11.4 迁移触发条件

- 需要复杂关系查询、跨城市大规模检索或强事务模型。
- 需要独立管理后台、多端开放 API、复杂风控或更严格的部署治理。
- 成本、并发、审计或数据治理要求超出当前云开发方案。

## 12. 数据模型（逻辑层）

| 集合/实体 | 关键字段 |
| --- | --- |
| `users` | openid 映射、状态、角色、成年确认、创建时间 |
| `profiles` | 昵称、头像、城市、兴趣、资料完整度 |
| `activities` | 发起者、类型、通用字段、类型扩展、人数、状态、版本、时间戳 |
| `applications` | 活动、申请者、状态、说明、批准后自动占位同意标记、唯一键 |
| `members` | 活动、用户、角色、加入/退出记录、有效状态 |
| `notifications` | 接收者、事件类型、关联对象、已读状态 |
| `completionRecords` | 完成/取消事实、参与者确认、异议 |
| `reviews` | 活动、评价人、目标、结构化标签、可见范围 |
| `reports` | 举报人、对象、类型、说明、证据、处理状态 |
| `riskEvents` | 规则、账号、活动、分级、处理结果 |
| `auditLogs` | 操作者、动作、对象、前后状态摘要、时间 |

### 12.1 关键数据约束

- `(activityId, applicantId)` 有效申请唯一。
- 批准占位使用事务和活动 `version`，任何时刻 `memberCount <= targetMembers`。
- 关键写接口接受幂等键，重复请求返回首次结果。
- 公开查询使用单独的安全视图/返回 DTO，绝不直接返回完整数据库文档。
- 所有状态变更同时写入审计事件。

## 13. 云函数/API 边界

- `auth.login`：接收小程序登录态，返回业务用户与会话结果。
- `profile.get/update`：最小资料读取与修改。
- `activity.create/update/publish/list/detail/cancel/complete`。
- `application.submit/approve/reject/withdraw/leave`。
- `group.getContact`：仅成团有效成员可调用，按需返回最小联系信息并记录访问审计。
- `notification.list/read`。
- `report.create/list/resolve`（运营权限隔离）。
- `moderation.checkText` 作为发布、申请、评价、举报链路中的内部服务。
- `admin.activity.suspend`、`admin.user.restrict`、`admin.audit.list`。

具体实现可合并为少量聚合云函数，外部动作名保持稳定，避免函数数量过多。

## 14. 非功能要求

- 关键写操作可重试且不重复扣占名额。
- 列表首屏在常规网络下具备骨架屏、超时和重试；不使用无限静默加载。
- 页面必须覆盖加载、空数据、权限拒绝、网络失败、内容受限、活动状态变化等状态。
- 服务端日志不记录完整联系方式、精确位置和微信敏感凭据。
- 按环境区分开发/测试/生产；敏感配置不写入代码仓库。
- 数据库索引、备份与恢复步骤写入部署说明。

## 15. 指标与 MVP 验收

### 15.1 产品指标

- 发布成功率。
- 活动发布到首个申请的转化。
- 申请批准率、批准后退团率、成团率、完成率。
- 取消率、撤回率、举报率、7/30 日再次发起或参与率。

### 15.2 功能验收

1. 游客可在不登录、不授权精确位置的情况下浏览；发布和申请按动作触发登录。
2. 三类活动都能发布、筛选、查看详情和申请。
3. 发起者能批准/拒绝；用户申请时已同意获批后自动占位，达到人数后自动成团。
4. 并发争抢最后一个名额不会超员，重复操作不会产生重复记录。
5. 过期、取消、撤回、满员、下架均有一致状态和用户提示。
6. 非成员无法读取成团后联系方式；有效成员通过独立鉴权接口只看到必要信息。
7. UGC 写入经过内容安全入口；违规或接口失败按策略阻止/待审。
8. 用户可以举报，运营角色可以处置，并生成审计记录。
9. 核心规则有自动化测试，关键页面有手工验收清单。
10. 项目能通过微信开发者工具导入，使用演示数据走通闭环。

## 17. 主要风险与缓解

| 风险 | 影响 | MVP 缓解 |
| --- | --- | --- |
| 拼车被理解为用户经营载客 | 合规与人身风险 | 仅同行撮合、禁司机招揽、固定提示、举报下架 |
| 商品诈骗或私下收款 | 财产纠纷 | 平台不收款、不担保、限制敏感文案、举报与封禁 |
| 搭子场景变成婚恋/骚扰 | 社交与内容风险 | 18+、活动导向、禁婚恋暗示、延迟联系、举报处置 |
| 冷启动没有内容 | 无法验证匹配 | 单区域试点、真实官方活动、模板化发布 |
| 成团后爽约 | 信任下降 | 申请时预先确认、锁定时间、取消原因、事件记录、后续再做降权 |
| 精确位置/联系方式泄露 | 隐私与安全 | 公开阶段隐藏、成团后最小披露、服务端 DTO 隔离 |
| 云开发被前端直连导致越权 | 数据泄露 | 所有业务写入走云函数，数据库安全规则默认收紧 |

## 18. MVP 实施决定

以下为 CCG 综合后的默认实施基线；用户可在实现过程中提出变更：

1. **首发范围**：三个入口都保留，底层共用；运营重点先放拼车和拼商品。
2. **年龄门槛**：MVP 仅 18+。
3. **拼车边界**：只允许同行者共同约用合规交通方式，不允许司机/车主招揽载客。
4. **拼商品边界**：只做凑单协作，不接支付、不担保、不放外部购买链接。
5. **拼好友边界**：改为“拼搭子”，必须绑定具体活动，不做婚恋。
6. **占位规则**：用户申请时同意获批后自动加入；发起者批准即事务占位，不设二次确认。
7. **隐私规则**：只有成团后的有效成员才能通过独立鉴权接口查看必要联系/会合信息。
8. **技术路线**：微信原生小程序 + CloudBase 云函数/数据库。
9. **试点范围**：单城市或演示环境，不默认全国公开运营。
10. **图片能力**：MVP 先不上传 UGC 图片，降低内容审核和开发复杂度。
11. **评价范围**：MVP 只做完成与举报，结构化评价延后到 P1。
12. **运营后台**：先做受权限保护的最小运营页面或管理脚本，不做完整 CMS。

## 19. Gemini 3.6 前端分析综合结果

- 已采纳：三 Tab、通用卡片骨架、两步发布、零登录浏览、结构化区域、任务驱动“我的”、主包/分包和统一 Service 层。
- 已修正后采纳：申请时预先同意、批准即占位；首次查看联系信息只做一次确认，不强制等待；订阅消息在模板未配置时降级。
- 延后：公开 Q&A、结构化评价、图片/二维码、信用分和复杂申诉。
- 不采纳：无来源的转化率数字、虚假的“实名/信用”徽章、强制手机号、关键业务 EventBus、未经验证的框架配置。
- 详细记录见 CCG 任务文件 `frontend-analysis.md`。
